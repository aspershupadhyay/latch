# Latch device protocol v1

The contract between a gateway and a phone. Independent of MCP. The normative definition is the Rust crate `crates/protocol`; the JSON Schemas in `packages/schemas/v1/*.schema.json` are generated from it (`LATCH_UPDATE_SCHEMAS=1 cargo test -p latch-protocol --test schema`), and every implementation must accept `packages/schemas/v1/fixtures/valid/*` and reject `.../invalid/*`.

## Full-access ADB (R27)

[ADR-046](../adr/README.md#adr-046--unrestricted-owner-authorized-adb-over-wireless-mcp) is a separately owner-enabled wireless MCP/ADB path with no extra Latch command restrictions after initial authorization and Android pairing. The `adb.shell` capability and command (protocol 1.17, below) are the versioned contract for it, with streaming/continuation for complete output rather than fixed caps. The ordinary command limits, confirmation/session timers, redaction, and app/file scope do **not** apply to this capability. The protocol, both gateways, the fake-device executor, and the Android on-device executor and cable-free pairing are implemented and tested; the end-to-end run on a real phone is still to be recorded (roadmap R27, `*needs phone*`).

Deadlines: for `adb.shell` the envelope's `deadline_ms` is the caller's `timeout_ms` when set. Otherwise the Rust gateway sends `4294967295` (no deadline) and the Vercel gateway its platform maximum (280 s, under the function's 300 s limit); a continuation (`continue_from`) gets the ordinary 20 s. The phone applies that deadline to the command (none for `4294967295`) and stops it on a `cancel` message, which a gateway sends when its wait ends or its caller goes away.

## Transport

- The phone opens `GET /v1/device` as a WebSocket with `Authorization: Bearer <device token>`. Use `wss://` outside development.
- Each text frame is one JSON message. Binary frames are a protocol error.
- Limits: phone → gateway frames ≤ 8 MiB; gateway → phone ≤ 64 KiB. The gateway pings every 20 s and drops a connection silent for 60 s.
- Version: `"1.2"` (see *Version history*). Peers are compatible when the major version matches; unknown fields must be ignored.

## Lifecycle

```text
phone                                   gateway
  ── hello {protocol, device, capabilities, session, device_time_ms} ──▶
  ◀── welcome {protocol, device_id, server_time_ms} ──
  ◀── command {id, deadline_ms, command:{name, params}, confirm?, observe_after?} ──
  ── result {id, outcome:{status:"ok", data} | {status:"error", error:{code, message}}} ──▶
  ── state {capabilities, session, device_time_ms}   (owner changed a switch, paused, resumed)
  ◀── cancel {id}                                    (best effort)
  ◀── revoked {reason}  then close 4003
  ── bye {reason}  then close                        (stop, expiry, unpair)
```

Close codes: 4001 expected hello, 4002 incompatible hello, 4003 revoked.

## Capabilities

`device.info`, `ui.observe`, `screen.capture`, `input.gesture`, `input.text`, `nav.global`, `app.launch`. Status per capability: `enabled`, `disabled`, `needs_permission`, `unsupported`.

## Observe after an action (since 1.2)

`observe_after {settle_ms (≤ 3000), include_screenshot, max_nodes}` may accompany an action command (never `device.info`, `ui.observe`, `app.list`). After the action succeeds, the phone waits `settle_ms`, then observes under exactly the rules of `ui.observe` (capabilities checked again at that moment, restricted screens refused) and answers with the action result plus `observation` (it becomes the latest observation), or `observation_error {code, message}` when it could not observe. The action has happened either way. Gateways send the field only to phones whose `hello` said 1.2 or later; this saves the second command a gateway would otherwise send to show the agent the new screen.

Since 1.3, `observe_after.quiet_ms` (≤ 1000) makes the wait adaptive: the phone observes as soon as the screen has not changed for `quiet_ms`, counted from the end of the action at the earliest, and after `settle_ms` at the latest. Gateways send 150 ms quiet within 1500 ms; 1.2 phones ignore the field, so gateways send them a fixed `settle_ms` instead.

`ui.wait` and `ui.scroll_to` match `text` case-insensitively against the text and description of elements that are neither sensitive nor editable (an input field holds what the agent typed, not the app's answer). `ui.scroll_to` stops early when the list stops moving. Gateways send 1.3 commands and fields (`submit`, `double`, `hold_ms`) only to phones whose `hello` said 1.3 or later, and otherwise answer `unsupported_capability` asking the owner to update the app.

## Confirmation

When `confirm {title, detail, risk, remember?}` is present, or the session has `approve_every_action`, the phone must show the request and wait for the owner before executing, answering `user_denied` or `confirmation_expired` otherwise. The phone may ask for approval even when the gateway did not.

Since 1.3, `remember` (1–160 characters, no control characters) is a key such as `tap|com.instagram.android|share`. When it is present the owner may answer *once*, *for this session*, or *always in this app*, and the phone answers later requests with the same key from its saved answers without showing the card. It is absent for critical actions (money, app installs, Android permission prompts, account deletion), which are asked every time, and in approve-every-action mode. Saved answers live only on the phone; the owner can remove them, and the phone ignores them when its own check of the live screen finds a critical action.

Since 1.4, while the phone waits for the owner on a running command it sends `approval_request {command_id, nonce, title, detail, kind: action | app, choices, remote, expires_at_ms}` (nonce: 32 lowercase hex; title ≤ 200 and detail ≤ 600 characters, no control characters; choices: 1–4 distinct of `once`, `session`, `always`, `deny`). Gateways then keep waiting for that command up to one approval deadline (120 s) beyond its own, and the phone keeps the question open up to 110 s. When `remote` is true (the owner's `session.remote_approvals` switch), a gateway may ask the AI app's user (MCP elicitation) and relay the answer as `approval_answer {nonce, choice}`; the phone applies it only if the nonce matches its open question, the choice was offered, and the switch is still on. The phone's own card stays up; whichever answer arrives first counts.

## Error codes

`invalid_request`, `unsupported_capability`, `permission_missing`, `policy_refused`, `sensitive_target`, `stale_observation`, `target_not_found`, `screen_protected`, `user_denied`, `confirmation_expired`, `cancelled`, `deadline_exceeded`, `device_unavailable`, `ambiguous_device`, `transport_unavailable`, `internal`. Codes are never renamed. Messages must not contain screen content, tokens, or personal data.

## Pairing (HTTP, outside the WebSocket)

`POST /v1/pair {code, platform, model}` → `200 {device_id, name, token, protocol, device_path}`, plus `owner_key` when the code was a setup code from the owner's terminal (`POST /v1/admin/pairings {"owner": true}`, shown as a QR code; ADR-054); `403` wrong or expired code; `429` too many wrong codes. The token is shown once and stored by the phone; the gateway keeps only its SHA-256.

## Version history

- **1.0** WebSocket transport.
- **1.1** HTTP long-poll transport for serverless gateways: `POST /v1/device/hello` (answered by `welcome` with a `connection` id), `GET /v1/device/poll?connection=…&wait=25` (200 with one message, 204 nothing yet, 409 send hello again, 401 revoked), `POST /v1/device/messages?connection=…` for results, state, and bye.
- **1.2** `observe_after` on action commands and `observation` / `observation_error` in action results. Polls may add `hot=1` while an agent is actively using the phone (the phone sends it for 60 s after each command) so the gateway checks for work more often; gateways ignore it otherwise.
- **1.6** Files and sharing (ADR-026). Capabilities `file.read`, `file.write`, `app.share` (gateways skip capability names they do not know, so later additions never break pairing). Commands: `file.list {location: photos|downloads|folder, folder?, query?, limit 1–200 (50), offset?}` → `FileList`; `file.preview {id}` → `FilePreview` (text up to 64 KB, or a downscaled image); `file.read {id, offset, length ≤ 524288}` → `FileChunk` (base64); `file.write {location, folder? (folder only), subfolder? (photos/downloads), name, mime?, data_base64 (≤ 512 KB raw), append?, overwrite?}` → `FileItem`; `file.mkdir {folder?, name}`, `file.rename {id, name}` → `FileItem`; `file.delete {id}`; `app.share {package, ids (1–10), text?}` → action result (with `observe_after`). Names: 1–120 characters, no `/ \ : * ? " < > |`, control characters, or leading dot. Ids are opaque, issued by the phone, valid for the session. An existing name gets a free name unless `overwrite`; `append` only adds to a file Latch wrote in this session. Gateways ask the owner (`confirm`, high risk) for `overwrite` and `file.delete`; the phone skips the question in Auto mode and when nothing would be replaced. File changes do not invalidate the latest observation. Gateways frames to the phone may now be 1 MiB. Whole files move through gateway links (`GET /v1/files/{token}`, `PUT /v1/uploads/{token}`, 256-bit tokens, 15 minutes; 64 MB self-hosted, 4 MB on Vercel), never through the AI's context.
- **1.5** `owner.ask {message}` (1–300 characters, no control characters except newlines; no capability): the phone shows the message with "Done" and "I can't" and answers an action result with `owner: done | cant | no_answer` (and `observe_after` as usual). Gateways give it the approval deadline (120 s). It is never relayed to the AI app and never asked about under "approve every action" (ADR-026). `type_text` results may carry `submitted: false` when Enter visibly did nothing (any 1.x phone may send it).
- **1.4** `session.remote_approvals`; `approval_request` (device → gateway) and `approval_answer` (gateway → device) for approvals answered in the AI app (see Confirmation, ADR-023). Gateways tolerate 1.3 phones, which never send them.
- **1.3** `confirm.remember` for saved approvals (see Confirmation); `ui.wait`, `ui.scroll_to`, `input.pinch`, `input.type.submit`, `input.tap.double`, `input.swipe.hold_ms`; `observe_after.quiet_ms`; `found` in action results.
- **1.7** Whole files by encrypted link, and the clipboard (ADR-027). Capability `clipboard.write`. Commands: `file.fetch {location, folder?, subfolder?, name, mime?, overwrite?, link, sha256, size?}` (download, decrypt, check, save like `file.write`; a file whose SHA-256 differs is never kept), `file.push {id, link, max_bytes}` (encrypt and upload), both answering a `FileTransfer {id, state: running|done, done_bytes, total_bytes?, item?, sha256? (push)}` at once or when done; `file.transfer {transfer, wait_ms ≤ 15000, cancel?}` follows one and answers the same, or the error that ended it; `clipboard.set {text ≤ 10000}` → action result. A `FileLink` is `{url (http(s), ≤ 4096), headers? (≤ 8, `x-…` or `content-type`, printable), key_hex (64), iv_hex (32)}`; stored bytes are always AES-256-CTR (128-bit big-endian counter, as `openssl enc -aes-256-ctr`) under a key made for that one transfer. Phones follow links only to their own gateway's origin and to Vercel Blob (`*.blob.vercel-storage.com`; uploads also `https://vercel.com/api/blob`), never through redirects. Gateways serve links at `PUT`/`GET /v1/blobs/{token}` when no external storage is used. The clipboard is never read.
- **1.8** The phone's activity log, and the end of a task (ADR-028). Capability `activity.read`. Commands: `activity.list {limit 1–500 (50), kinds? (≤ 10 of session, connection, screen, action, app, approval, refusal, file, folder, task), since_ms?}` → `ActivityList {entries: [{at_ms, kind, summary, app?, by?}] newest first, total}`; `by` (optional, added within 1.8; older phones leave it out) is `ai`, `owner` (the owner's own tap or answer), or `latch` (a timer, a rule, the connection); entries never hold screen content, typed text, or file contents. `task.done {summary? ≤ 500, no control characters but newline and tab}` (no capability, not an action) → action result: the phone hides its cursor and logs the summary. With several shared folders, `file.list {location: folder}` without `folder` lists the folders themselves, and other folder commands need a `folder` id.
- **1.9** Action results with `observe_after` carry `effect`: `none` (the screen looks the same as before the action, judged after it settled: the action may have missed), `changed` (the same app shows something different), or `new_app` (another app is in front). An unreadable screen is reported as `changed`, never as a miss. Gateways tell the AI when an action had no visible effect. Older phones leave it out (roadmap R11).
- **1.10** Screenshots may be `image/webp` (lossy, quality 70: about 40 % smaller than JPEG at the same quality on rendered phone pages). Phones send WebP only to gateways that answered `hello` with 1.10 or later and JPEG otherwise (roadmap R6).
- **1.11** Phone controls (ADR-035, roadmap R16). Command `device.control {control}`, where `control` is one of `{kind: volume, stream: media|ring|notification|alarm, percent 0–100}`, `{kind: media, action: play_pause|next|previous}`, `{kind: brightness, percent 0–100}` (adaptive brightness turns off), `{kind: flashlight, on}`, `{kind: panel, panel: wifi|internet|bluetooth|volume}` → action result. Each group needs its own capability, off by default: `control.sound` (volume and media), `control.brightness` (the phone reports `needs_permission` until the owner allows Android's "Modify system settings"), `control.flashlight` (`unsupported` without a flash), `control.panels`. Only a panel changes the screen and takes `observe_after`; taps inside it are ordinary actions. Gateways never send `device.control` to phones older than 1.11.
- **1.12** Device keys (ADR-037, roadmap R19). `hello.device_key` (base64 SPKI DER of a P-256 key) and the message type `signed {payload, sig}`: `payload` is another device message's JSON text exactly as signed, `sig` an ECDSA P-256 / SHA-256 DER signature (base64) over `latch-signed-v1\n<connection>\n<payload>`, with `<connection>` the welcome's `connection` (empty for `hello`; WebSocket welcomes now name one too). A hello with a key must be signed by it and registers it; after that the gateway refuses unsigned messages, other keys, and bad signatures (HTTP 401 / WebSocket close 4004). Phones that never sent a key stay unsigned. Test vector: `packages/schemas/v1/signing/vectors.json`.
- **1.21** Timers and alarms (roadmap R71, ADR-073). `device.control` gains `{kind: "timer", seconds}` (1–86400) and `{kind: "alarm", hour, minute}` (0–23, 0–59), set in the phone's clock app through Android's `AlarmClock` API without opening it; both sit behind the settings-pages switch (`control.panels`). A phone without a clock app that takes them answers `unsupported_capability`. Gateways send them only to phones on 1.21 and up.
- **1.20** ADB jobs (ADR-049, roadmap R29 d). `adb.shell` gains `background?` (with `command_line`, not with `base64`): the phone starts the command and answers at once with `AdbResult.job` and `job_state: "running"`. `adb.shell {job, wait_ms?, cancel?}` (instead of `command_line`/`continue_from`, without `stdin`) answers with what the job wrote since the last collection, after waiting up to `wait_ms` for it to finish; `job_state` is `running` while it runs or output is left, `finished` with `exit_code` once all of it was read, and `cancelled` after `cancel`. After `finished` or `cancelled` the id is forgotten. Chunks past a frame use `cursor`/`continue_from` as before. The job keeps running between commands and across reconnects; owner Stop, turning the capability off, or an app restart ends it and deletes its output. Latch imposes no limit on a job's length or output (ADR-046). Gateways send `background` and `job` only to phones on 1.20 and up.
  Also in 1.20, all optional and ignored by older peers (R67): `UiNode.ocr` (words the phone read from the screen's pixels; a tap lands at the centre of `bounds`), `ActionResult.level` (`device.control` volume: `step`, `max_step`, `percent` as Android set them), `FileItem.subfolder` (photos and Downloads), `SessionInfo.files` (`photos`, `folders`: the places the owner shares), and the gateway message `refused {tool, code}` (a tool call the gateway refused before it reached the phone, for the owner's activity log; content-free, older phones drop it).
- **1.19** A command survives a reconnect and runs at most once (ADR-048, roadmap R29). No new fields. When a phone reconnects while a command is in flight, the gateway sends the same `command` envelope again, same `id`, to a phone on 1.19 and up. The phone must run each id at most once: it ignores an id it is still running, answers an id it already answered with the same answer, and answers an id it ran but no longer remembers `cancelled` without running it. An answer counts on whichever of the phone's connections it arrives. After `bye`, commands in flight fail and are never resent. Gateways resend only to phones on 1.19 and up.
- **1.18** Gestures and binary ADB output (ADR-047, roadmap R28). Command `input.gesture {observation_id, strokes: [{points: [{x, y}] (1–64), start_ms? (0), duration_ms}] (1–10)}` → action result; every stroke ends within 15 000 ms. A stroke whose points all stay within 32 px of its first point is judged as a tap, or a long press at 400 ms or more, by gateways and phone, exactly as `input.tap` (this also applies to `input.swipe` from now on). `adb.shell` gains `base64?` (with `command_line` only): stdout carries base64 of the exact bytes, chunked like text. Gateways no longer hold the per-phone command lock for `adb.shell`, and phones run it beside screen commands. Gateways send `input.gesture` and `base64` only to phones on 1.18 and up.
- **1.17** Full-access ADB (ADR-046, roadmap R27). Capability `adb.shell`, off by default and outside the UI/file scope and approval rules. Command `adb.shell {command_line? (≤ 128 KiB), stdin? (≤ 512 KiB), timeout_ms? (caller-requested; Latch imposes none), continue_from?}` → `AdbResult {stdout, stderr, exit_code? (with the final chunk), cursor? (more output remains)}`. Exactly one of `command_line` or `continue_from` is given. The command line passes to the device's ADB executor unchanged: Latch adds no allowlist, per-command approval, output filter, or quota, and the capability is gated only on the owner enabling it (and authorizing Android wireless debugging) and on owner Stop/pause; it keeps working past the ordinary session timer. Output that does not fit a frame is chunked and resumed with `continue_from`, and the whole result goes only to the authenticated client and is never logged. Gateways send it only to phones on 1.17 and up. Android's own ADB permissions set the actual boundary.
- **1.16** More of the accessibility tree (ADR-044, roadmap R26). `UiNode` adds optional `state` (string), `hint` (string), `selected` (bool), `heading` (bool), `position {index ≥ 0, count?}`, `percent` (0–100), `actions` (≤ 16 strings, the app's own extra actions), `label` (a guessed name for an element without text or description: tooltip, `labeledBy`, or resource id words), and `covered` (bool: under another window of the app). Their lengths count toward the element's text limit; sensitive elements carry none of them. `ui.observe.marks` (bool, default false) asks for each listed element's id drawn on the screenshot. Older peers ignore all of these.
- **1.15** More buttons, links, status, and controls (ADR-043, roadmap R25). `nav.global.action` adds `lock_screen`, `screenshot`, `split_screen`, and `dpad_up|dpad_down|dpad_left|dpad_right|dpad_center` (no notification shade or quick settings). `app.launch.fresh` (boolean, default false) starts the app from its first screen. New command `app.open_link {url, package}` (capability `app.launch`; ≤ 2048 printable ASCII, lowercase scheme, `intent:`/`android-app:`/`file:`/`content:`/`javascript:`/`vbscript:`/`data:`/`blob:`/`about:`/`filesystem:`/`jar:` refused) opens the link in that app only, answering an action result. `device.info` adds optional `status {battery_percent?, charging?, network? (wifi|cellular|ethernet|none), free_storage_mb?, orientation? (portrait|landscape), locked?, do_not_disturb?}`. `device.control` adds `{kind: ringer, mode: normal|vibrate|silent}`, `{kind: do_not_disturb, on}` (capability `control.sound`), `{kind: rotation, mode: auto|portrait|landscape}`, `{kind: screen_timeout, seconds 15–1800}` (capability `control.brightness`), and the panels `nfc`, `airplane_mode`, `location`, `display`, `battery`, `sound`, `notifications`, `storage`, `date_time`. Gateways send each new command or value only to phones on 1.15 and up.
- **1.14** Same-Wi-Fi fast lane (ADR-041, roadmap R23). Command `file.local {direction: receive|send, max_bytes 1..2^31}` (capability `file.write` to receive, `file.read` to send; not an action) answers `LocalSlot {url, expires_at_ms}`: a one-transfer address `http://<private, loopback, or link-local IPv4>:<port ≥ 1024>/<64 lowercase hex>` that gateways check and otherwise ignore. A later `file.fetch` or `file.push` whose link URL is that address reads what the computer `PUT` there, or encrypts into it for one `GET`, instead of using the network. Phones answer `unsupported_capability` when the owner's switch is off, they are not on Wi-Fi, or they do not implement it; gateways then use the cloud link. Gateways send it only to phones on 1.14 and up.
- **1.13** Battery optimisation (ADR-040, roadmap R13). Optional `hello.battery_restricted` (boolean): true when Android's battery optimisation applies to the app, so Android may stop it in the background. Gateways keep it with the live connection and `diagnose` tells the owner to set battery use to Unrestricted. Older gateways ignore the field; it is read at each hello, so a change shows after the next reconnect.
